# 优化历程：每一步做了什么、为什么、值多少分

> 这份文档回答两个问题：**检索分数是怎么从 80.9% 变成 94.4% 的**，
> 以及**检索分数到答对之间，丢掉的那部分去了哪里**。
> 按时间顺序写，包括走过的弯路和踩过的坑——那些才是面试真正能讲的东西。
>
> 本项目最初用的是合成基金语料，后来整体换成了《喜羊羊与灰太狼》×《铁甲小宝》的角色关系。
> 本文的数字全部来自新语料；早期语料上的几个重要发现放在最后一节。

---

## 先建立一个认识：这个项目在优化什么

**检索的核心指标是 `recall@10`**：问一个问题，系统检索出 10 段资料，
其中覆盖了多少份"标准答案所需的证据文档"。

为什么盯着这个指标？

> **检索召不回的证据，生成阶段无论如何也补不回来。**
> recall 是整个系统的天花板。先把天花板抬高，再去优化生成。

```
recall@10 = 召回的证据文档数 / 该题所需的证据文档总数
```

这个指标能算出来，是因为**语料是从图谱渲染出来的**：
题目是人写的，但每道题声明了它依赖图里的哪几条边，证据文档是从边上查出来的，不是人工标的。

**但 recall 不是全部。** 第 6 步会讲到：recall 100% 的题，答对率可以只有 25%。

---

## 语料与题库

```
事实来源   维基百科等公开资料，只收至少一个来源明确写出的事实
实体 49    节目 2 / 角色 38 / 地点 4 / 团体 2 / 道具 3
边   174   实体关系 19 种 + 属性 19 种
文档 42    角色档案 31 / 名册 3 / 团体 2 / 剧情与设定 4 / 节目简介 2
题库 109   9 种能力，train 45 · dev 23 · test 41
```

四个刻意的难度设计：
- **每条关系只写在一份文档里**："小灰灰的父亲是灰太狼"只在小灰灰的档案里。于是"小灰灰的爷爷"必须拼两份文档
- **名字高度雷同**：喜羊羊/美羊羊/懒羊羊，灰太狼/红太狼/蕉太狼/香太狼/灰二太太狼
- **证据只写别名**：剧情梗概里只写「高圆寺博士」，别名只在本人档案里声明一次
- **指代与列表**：档案第二、三节全部用「该角色」；居民登记、阵营一览是「标题 + 列表项」

## 起点：80.9%

最朴素的做法——把文档切块、建 BM25 关键词索引、检索 top-10。

| 题型 | recall@10 |
|---|---|
| 单跳事实（原词 / 改写 / 易混） | 100% / 93.8% / 100% |
| 纯语义（问题里没有角色名） | 33.3% |
| 两跳关系 | 67.5% |
| 三跳关系 | 76.7% |
| 关系路径（A 和 B 是什么关系） | 80.0% |
| 列举比较 | 90.0% |
| **总计** | **80.9%** |

语料只有 42 份，BM25 的起点比大语料高得多。**后面所有的工作都是在解决中间那几行。**

## 第 1 步：切块策略（没涨分，但发现了真问题）

### 问题

角色档案里，角色名只出现在第一句："小灰灰是动画《喜羊羊与灰太狼》中的角色。"
第二、三节全部用「该角色」指代。按章节切块后，第三节那一块长这样：

> 三、人物关系　该角色的父亲是灰太狼。该角色的母亲是红太狼。

**它不含"小灰灰"三个字。** 问"小灰灰的爸爸是谁"，这块很难被搜到。这叫**孤儿 chunk**。

### 做法

给每个 chunk 补上「小灰灰 角色档案｜三、人物关系」前缀（只加到用于检索的文本里，
不加到展示的原文里，否则引用会指到原文不存在的文字上）。

### 结果（recall@1，BM25）

| 策略 | 单跳事实（原词） | 单跳事实（改写） | 易混角色 | 总计 |
|---|---|---|---|---|
| 按章节切 | 66.7% | 37.5% | 58.3% | 43.2% |
| **补上下文** | **77.8%** | **68.8%** | **87.5%** | **57.1%** |
| 定长切 | 88.9% | 50.0% | 87.5% | 56.4% |

### 这一步真正的收获

定长切块（每 350 字切一刀）的总分和"补上下文"几乎一样。
但**机制完全不同**：档案平均只有 300 字，定长切块基本是**一份文档一块**（50 块 vs 187 块），
角色名和事实**碰巧**装进了同一块。文档再长一点它就会失效。

> **只看总分会得出错误结论，必须看机制。**

---

## 第 2 步：加向量检索（纯语义 33% → 75%）

### 问题

BM25 是按字面匹配的。问"哪只羊一开口说坏事就会应验"，
文档里写的是"有一张乌鸦嘴，预言坏事很准"——**一个 4 字片段都对不上**。

### 做法

用 `bge-small-zh` 把每段文本转成 512 维向量，按语义相似度检索。

模型选的是**量化版 ONNX**，24MB，随仓库分发，第一次运行就完全离线。
不用 sentence-transformers 是因为它要装几百 MB 的 torch，而且首次运行要联网下模型——
**"能搬到别人的 Windows 上"是这个项目的硬约束**。

### 结果

| | BM25 | Dense | BM25+Dense |
|---|---|---|---|
| 纯语义题 | 33.3% | **75.0%** | 66.7% |
| 总计 | 80.9% | 88.2% | 87.0% |

### 这一步真正的收获

`semantic_only` 题的设计前提是"问题用词在语料中不出现"。这个前提写了脚本验证：
**12/12 题与语料没有任何 4 字以上的重叠**。不验证的话，BM25 靠某个碰巧重合的词蒙对，实验就失效了。

另一个细节：**BM25+Dense 融合在纯语义题上反而比纯 Dense 低**（66.7% vs 75.0%）——
BM25 的高排名噪音把向量的正确结果挤掉了一部分。这个缺口至今没补上（见已知缺口）。

---

## 第 3 步：知识图谱检索（关键一步）

### 问题

"小灰灰的爷爷是谁？"

- 小灰灰的档案写着"该角色的父亲是灰太狼"
- 灰太狼的档案写着"该角色的父亲是黑太狼"

第二份文档**一个字都不提小灰灰**。关键词检索和向量检索都是"找像问题的文本"，
而灰太狼的档案和这个问题一点都不像。

### 做法

从问题里认出实体（最长匹配："灰二太太狼"不能被"灰太狼"吃掉），
沿着图上的边**走**到证据所在的文档，而不是**找**像问题的文本。
每条边都记着它来自哪份文档，走过的路径直接就是证据清单。

### 结果

| 题型 | BM25 | 图检索 |
|---|---|---|
| 两跳关系 | 67.5% | **100%** |
| 三跳关系 | 76.7% | **100%** |
| 关系路径 | 80.0% | **100%** |
| 纯语义 | 33.3% | **0.0%** ← 注意这个 |

图检索在纯语义题上是 0——问题里没有角色名，图没有起点。**没有一种检索能包打天下。**

### 堆 k 能不能追上？

```
两跳题 recall@k        k=1   k=3   k=5   k=10   k=20
  BM25                 40%   60%   62%    68%    82%
  Graph(标准图)        42%   95%  100%   100%   100%
```

早期基金语料上，BM25 放大 20 倍后在 50% 左右饱和，结论是"加大 k 无解"。
**新语料太小，这个结论不能照搬**：k=20 时关系路径题 BM25 也到了 100%。
能成立的说法是：**图检索 5 块拿全，BM25 要 20 块、而且两跳题仍只有 82%**——
语料只有 42 份，20 块已经接近把半个语料库塞进上下文。

## 第 4 步：枢纽节点

两个节目节点（《喜羊羊与灰太狼》《铁甲小宝》）各连着 15～16 个角色。
如果允许从节目节点中转，同一部剧里任意两个角色都"有关联"——关系图谱里最常见的假阳性来源。

做法：连接数超过 12 的节点**不允许作为中转**（仍可作为终点）。它是一个可消融的参数。

| 题型 | 阻断 | 不阻断 |
|---|---|---|
| 关系路径 | **100%** | 90.0% |
| 三跳关系 | **100%** | 93.3% |

在第 6 步加入关系链模板之前，无差别邻域扩散下阻断能把两跳题从 70% 拉到 100%；
加了之后差距变小，因为**只沿指定关系走的模板本身就不走 APPEARS_IN 边**。

阈值的代价：「羊村」只连着 8 条边，没到 12，于是"喜羊羊和灰太狼是什么关系"会找到一条
4 跳弱关联：喜羊羊住羊村 → 暖羊羊也住羊村 → 蕉太狼是暖羊羊的好朋友 → 灰太狼是蕉太狼的二叔。
不算错，但也不是一般人说的"关系"。

## 第 5 步：融合 vs 路由（一个没复现的结论）

### 早期的结论

早期基金语料上，把 BM25 和图检索用 RRF 等权融合，**分数反而被拉垮**：
聚合题从 92.3% 掉到 51.1%。于是改成**查询路由**：先判断这个问题该问谁，
主路优先出结果，剩余名额才给备选。

### 新语料上的实测

```
RRF(BM25+Graph)        89.7%
RRF(BM25+Dense+Graph)  92.9%
Routed                 94.4%    ← 关系路径 90% → 100%，三跳 93.3% → 100%
```

**旧结论没有复现**：两路融合 89.7%，比 BM25 和图检索单独用都高。路由仍然最好，但只好 1.5 个点。

### 这一步真正的收获

一开始我拿来比的是"BM25 + Graph"两路融合 vs 路由（路由的词面侧是 BM25 + Dense），
差距 4.7 个点——**其中一半来自有没有向量这一路，和"融合还是路由"无关**。
补上三路等权融合这个对照组之后，才是公平比较。

> **消融实验里最容易出错的不是实验组，是对照组。**

## 第 6 步：检索 recall 100%，答对率 25%（最值得讲的一步）

### 现象

第一次跑端到端评测（DeepSeek，三版 answer prompt）：

| 题型 | 检索 recall | 答对率（v1 / v2 / v3） |
|---|---|---|
| 两跳关系 | 100% | 30% / 25% / 25% |
| 三跳关系 | 100% | 40% / 40% / 40% |

模型一直回答"资料中未提及小灰灰的爷爷是谁"。

### 定位

把送进模型的上下文打出来：

```
[1] 小灰灰 角色档案        （标题块）
[2] 青青草原居民登记
[3] 灰太狼 角色档案        （标题块）  ← "父亲是黑太狼"在第三节, 没发出来
[4] 红太狼 角色档案        （标题块）
...
```

图检索按文档轮转发 chunk，**每份文档先发第一块**——而第一块是
「小灰灰 角色档案 + 资料来源说明」，不含任何事实。
**recall 按文档算，只要文档里任何一块被召回就算命中**，于是指标显示 100%。

### 三处修复

1. **关系链模板**：认出问题里的关系词（爷爷 → PARENT_OF / GRANDPARENT_OF，表哥 → COUSIN_OF，
   老婆 → SPOUSE_OF，原型 → PROTOTYPE），只沿这几种边走。
   否则"灰太狼表哥的老婆是谁"从灰太狼出发，一跳就连着 7 份文档，第二跳的香太狼档案排不进 top-8。
   走到的终点实体再补上它自己的档案——"美羊羊喜欢的那只羊有什么爱好"，爱好只写在喜羊羊的档案里
2. **文档内挑块**：优先发提到这条边两端名字的那一块。两处去噪都是实测撞上的：
   先抹掉节目名（「喜羊羊与灰太狼」里就含着「灰太狼」），不数档案主人自己的名字（它只出现在第一块）
3. **短前言并入第一节**：标题 + 资料说明不再单独成块

### 结果

| 题型 | 修复前（v3） | 修复后（v3） | 修复后（v1） |
|---|---|---|---|
| 两跳关系 | 25% | **85%** | 90% |
| 三跳关系 | 40% | **80%** | 100% |
| 可答题总答对率 | 70.1% | **88.7%** | 90.7% |

检索 recall@10 几乎没变（94.9% → 94.4%），**答对率涨了近 20 个点**。

> **指标没错，但它量的不是我以为的东西。** 文档级 recall 回答的是"证据文档来了没有"，
> 不回答"写着证据的那一段进没进上下文"。

## 第 7 步：抽取 prompt（三个真实发现）

图检索用的图谱，最终要从文档里抽出来。四版 prompt，DeepSeek，42 份文档：

| 版本 | precision | recall | F1 | 发生了什么 |
|---|---|---|---|---|
| v1 朴素 | — | 0% | 0% | 42 份里 40 份解析失败 |
| v3 schema + few-shot | 98.0% | 86.2% | 91.7% | 列表型文档整份跳过 |
| **v4 结构感知** | 96.7% | **100%** | **98.3%** | |

### 发现 1：不给 schema，输出契约会漂移

v1 只说"抽三元组，以 JSON 输出"。模型自己发明了 `{"entities": [...], "relations": [...]}` 格式，
关系名是"首播时间""出品公司"这样的中文短语，而且把"爷爷"抽成了一个独立实体。
下游图查询依赖固定的关系名，**一条都用不上**。

### 发现 2：约束过头会压制合法行为

v3 在负例里写了"只抽明确陈述的事实，不推理"。结果：

| 关系 | v3 recall | v4 recall |
|---|---|---|
| LIVES_IN（居民登记） | 0% | 100% |
| FACTION（阵营一览） | 0% | 100% |
| STUDENT_OF（学生名册） | 20% | 100% |

居民登记是这样写的：

```
一、羊村居民
　　· 喜羊羊
　　· 美羊羊
```

**没有一句话写着"喜羊羊住在羊村"**，模型把"读懂排版"当成了"推理"，整份跳过。
v4 把规则细化为"不许臆测，但必须读懂文档结构"，并补了一个列表型正例。
precision 从 98.0% 降到 96.7%——这个代价在 v4 的 hypothesis 里预先写了。

### 发现 3：模型对这两部动画的记忆，是抽取的风险源

v3/v4 都加了一个负例："文档没写飞翔机器人的原型，就不要输出 PROTOTYPE——哪怕你觉得'飞翔'听起来像鸟。"
evidence 回查（每条三元组必须附原文片段，逐字比对）在 v3/v4 两版里都没有拦下编造的三元组——
**但这不代表没有风险**，只说明这批语料上 DeepSeek 没有越界。

## 第 8 步：实体消歧（换题材后重写了一遍）

### 公司名的规则，搬到角色名上全错了

早期的消歧规则是为公司名设计的："星海资管"⊂"星海资产管理有限公司"，子串基本就是简称。
角色名里却经常相反：

| 子串关系 | 实际 | 踩坑经过 |
|---|---|---|
| 「和平星」⊂「射手座和平星」 | 总称与个体 | 规则抽取首跑就把三颗和平星并成了一颗 |
| 「卡布达」⊂「卡布达巨人」 | 机器人与它的变身形态 | 加了"前两字相同"限制后，LLM 抽取把卡布达巨人抽成了实体，又被并掉 |
| 「慢羊羊」⊂「慢羊羊村长」 | 同一只羊 | 这才是真简称 |

**词面分不出这三种情况。**

### 最终方案：四级级联 + 两条一票否决

```
0. 文档声明的「又名」    "吉祥寺藏之助又名藏之助" → 直接合并。最强证据, 免费
1. 规范化后完全相同      去标点、空白、大小写
2. 前两字相同            进入灰区, 交 LLM 裁决(卡布达 vs 卡布达巨人 -> 驳回)
3. 其余                  一票否决(喜羊羊 vs 美羊羊, 向量再像也不合并)

cannot-link: 同一份文档里有关系边相连的两个名字, 必不是同一实体
             (高圆寺寅彦是高圆寺让的爷爷 —— 两个名字前三个字相同, 向量高度相似)
```

v4 抽取图上：声明别名合并 3 对，词面一票否决 33 对，关系边一票否决 12 对。
v3 抽取图上 LLM 裁决过 1 次，正是「卡布达 vs 卡布达巨人」：`{"same": false, "reason": "卡布达巨人是卡布达的巨人形态/变身形态……"}`。
3 处"证据只写别名"全部接上。

### 这一步真正的收获

> **有确定性证据时，不要让模型去猜。** 文档自己写着"又名"，就是最好的消歧依据；
> 向量只负责**提名**候选，不负责拍板。

## 第 9 步：Prompt A/B 与"评测代码的 bug"

三版 answer prompt：v1 无约束 → v2 强制引用 → v3 拒答护栏。

### 第一版报表

| 指标 | v1 | v2 | v3 |
|---|---|---|---|
| 陷阱题正确拒答 | 91.7% | 83.3% | 100% |
| 可答题误拒答率 | 7.2% | 7.2% | 20.6% |

看起来：v2 编了两道陷阱题，v3 矫枉过正。

### 翻开原文

- v2 "编的"两道：**"根据提供的参考资料，没有关于卡布达体重的信息。"** ——它拒答了，
  只是"没有关于"不在拒答关键词表里
- v3 的误拒答里有 5 道关系路径题，**全部答对了**（"儿女亲家""表亲"），
  只是开头先写了一句"资料中未提及黑太狼与爹爹狼之间的直接关系"

### 修判分器

补全拒答措辞；误拒答改为"拒答**且**没答对"。重新判分（不需要重新调模型）：

| 指标 | v1_naive | v2_cited | v3_guarded |
|---|---|---|---|
| 可答题答对率 | **90.7%** | **90.7%** | 88.7% |
| 陷阱题正确拒答 | 100% | 100% | 100% |
| 可答题误拒答率 | **6.2%** | 7.2% | 11.3% |
| 引用命中标准证据 | 86.9% | **92.1%** | 91.7% |

> 本表是**关键词判分**口径（与历史结果可比）。关键词判分对关系类题偏宽，用 LLM 判官复判后，v3 的可答题答对率从 88.7% 降到 86.6%，见 [07-Agent](07-Agent.md)。

v3 的 hypothesis 写的是"陷阱题拒答率应大幅上升；风险是矫枉过正"。
**收益没发生**——连无约束的 v1 都是 100% 拒答；**风险应验**——误拒答 6.2% → 11.3%。

> **评测代码本身也要被评测。** 判分器的漏判，在报表上看起来和模型的幻觉一模一样。

### 抽取图 vs 标准图

| | 抽取图 | 标准图 |
|---|---|---|
| 检索 recall@10（图检索单独） | 82.0% | 82.0% |
| 可答题答对率（v3） | 88.7% | 89.7% |

v4 抽取 recall 100%，没有漏边，但端到端仍差 1 题（q-0088）：抽取图**多记**的一份来源文档占掉一个检索名额，把「阵营一览」挤出了 top-8。**不漏边不等于没损失**——多出来的边同样会挤占固定的检索预算。
（早期基金语料上这个差距是 24.6 分——那时的抽取 recall 只有 76%。）

## 第 10 步：让模型自己编排工具（Agent）

**问题：** 固定流水线是"路由 → 一次性检索 8 段 → 生成"。取漏了证据就没有机会补。能不能让模型自己决定查什么、查几次？

**做法：** 把图谱查询和检索做成 MCP Server 的 7 个工具（见 [06-MCP](06-MCP.md)），让 DeepSeek 在一个循环里自己调用，最多 8 轮。在同一模型、同一抽取图谱、同一判分下，和固定流水线比较全部 109 题。

**结果：**

| | 固定流水线 | Agent |
|---|---|---|
| 端到端答对率 | 88.1% | **97.2%** |
| 可答题误拒答率 | 13.4% | 1.0% |
| 陷阱题正确拒答 | 100% | 100% |
| 成本 | 基准 | **约 12 倍** |

提升全部来自两跳、列举、语义类题，简单题两边打平。

**这一步最值得讲的不是分数，而是评测本身被改准了三次：**
1. 关键词判分对关系类题放水（提到了人名、结论却是"无法确定"也判对），引入 LLM 判官，并分校准集 / 留出集报告一致率
2. 花费上限的口径错了，全缓存时也会"超支"并静默跳题，一度让结果虚高到两边都是 100%
3. 两道失败题的归因最初都写错了，是在回放页面上逐轮核对轨迹才纠正的

注意：这里的 88.1% 是 LLM 判官口径（含陷阱题）；上面几步里的端到端数字是关键词判分口径，两者不能直接比。

完整实验、失败分析和局限性见 [07-Agent](07-Agent.md)。

## 附：早期基金语料上的发现

这些发现来自换题材之前的版本，机制与语料无关，代码里的相应处理都保留着：

- **遍历穿过字面量节点**：两只基金因为最低认购额都是"25 万新元"，被判定为存在关联。
  字面量是属性值，不是实体，**不得作为中转**（`store/graph.py` 的 `steps_from`）
- **内存里对、落盘后错**：多来源溯源信息塞在 `__dict__` 里，`asdict()` 序列化时被静默丢弃。
  现在是 `Edge.extra_docs` 正式字段
- **向量相似度 1.00 却是两家不同公司**：中文向量模型对纯英文串的表示坍缩到同一点。
  由此确立"单一信号永远不足以触发合并"
- **train/test 划分泄漏**：按自增 id 分桶，同一问题文本落进了不同划分。现在按问题文本哈希分桶
- **缓存跨平台失效**：ONNX 浮点运算在 macOS 与 Linux 上 top-k 排序有细微差别，
  含检索结果的缓存键对不上。加了一层"语义稳定键"兜底（见 [05-部署说明](05-部署说明.md)）
