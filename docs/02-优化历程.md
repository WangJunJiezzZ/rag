# 优化历程：每一步做了什么、为什么、值多少分

> 这份文档回答一个问题：**分数是怎么从 65.2% 变成 86.3% 的。**
> 按时间顺序写，包括走过的弯路和踩过的坑——那些才是面试真正能讲的东西。

---

## 先建立一个认识：这个项目在优化什么

**核心指标是 `recall@10`**：问一个问题，系统检索出 10 段资料，
其中覆盖了多少份"标准答案所需的证据文档"。

为什么盯着这个指标，而不是直接看"答案对不对"？

> **检索召不回的证据，生成阶段无论如何也补不回来。**
> recall 是整个系统的天花板。先把天花板抬高，再去优化生成——
> 顺序反了就是在给天花板刷漆。

```
recall@10 = 召回的证据文档数 / 该题所需的证据文档总数
```

这个指标能算出来，是因为**语料是我们从图谱渲染出来的**，
每道题需要哪几份文档是推导出来的，不是人工标的。这是整个项目的地基。

---

## 起点：65.2%

最朴素的做法——把文档切块、建 BM25 关键词索引、检索 top-10。

| 题型 | recall@10 |
|---|---|
| 单跳事实（3 类） | 100% |
| 纯语义（问题里没有实体名） | 22.8% |
| 两跳关系 | 61.9% |
| 四跳风险穿透 | 45.0% |
| 共同董事 | 31.2% |
| 聚合计数 | 37.5% |
| **总计** | **65.2%** |

单跳题已经满分了。**后面所有的工作都是在解决剩下那几行。**

---

## 第 1 步：切块策略（没涨分，但发现了真问题）

### 问题

招募说明书里，"星海亚洲机会基金"写在第一节，
"本基金最低认购金额为 10 万新元"写在第四节。

按章节切块后，第四节那一块长这样：

> 合资格投资者参与**本基金**的最低认购金额为 10 万新元…

**它不含任何基金名。** 问"星海基金最低投多少"，这块永远搜不到。
这叫**孤儿 chunk**。

### 做法

给每个 chunk 补上文档标题作为前缀（只加到用于检索的文本里，
不加到展示的原文里，否则引用会指到原文不存在的文字上）。

### 结果

| 策略 | 单跳事实 recall@1 | 易混实体 recall@1 |
|---|---|---|
| 按章节切 | 58.3% | 63.6% |
| **补上下文** | **100%** | **100%** |

### 这一步真正的收获

定长切块（不管结构、每 350 字切一刀）的总分和"补上下文"差不多。
但**机制完全不同**：定长切块的块更大，**碰巧**把基金名和金额装进了同一块。
文档再长一点它就会失效。

> **只看总分会得出错误结论，必须看机制。**
> 这是整个项目里第一个"数字对了但理解错了"的例子。

---

## 第 2 步：加向量检索（+5.3 分）

### 问题

BM25 是按字面匹配的。问"哪些基金用程序化模型捕捉市场中性收益"，
文档里写的是"量化对冲策略"——**一个字都对不上**。

### 做法

用 `bge-small-zh` 把每段文本转成 512 维向量，按语义相似度检索。

模型选的是**量化版 ONNX**，24MB，随仓库分发，装机只要 50MB，
第一次运行就完全离线。不用 sentence-transformers 是因为它要装几百 MB 的 torch，
而且首次运行要联网下模型——**"能搬到别人的 Windows 上"是这个项目的硬约束**。

### 结果

| | BM25 | +向量 |
|---|---|---|
| 纯语义题 | 22.8% | **63.6%** |
| 总计 | 65.2% | 70.5% |

### 这一步真正的收获

我一开始设计的"同义改写题"，BM25 居然能拿 100%。
跑了评测才发现：**我的改写题里仍然带着基金全名**，
BM25 靠基金名的字符匹配就定位到了，根本没考到语义。

于是补了一类 `semantic_only` 题：**问题里不含任何实体名，
且用词在全部语料中一次都没出现过**（写了脚本验证，12/12 题零词面重叠）。
这才是真正的向量测试。

> **不做评测，你甚至不知道自己在测什么。**

---

## 第 3 步：知识图谱检索（关键一步）

### 问题

有一类问题，**无论 top-k 取多大都做不对**：

> "星海亚洲机会基金是否与高风险管辖区的实体存在关联？"

答案要把四份互不相干的文档串起来：

```
招募说明书    ：星海基金的管理人是星海资管
董事公告 A    ：李明是星海资管的董事
董事公告 B    ：李明是宏远国际的董事      ← 这份完全不提"星海"
注册摘要      ：宏远国际注册在卡瑟尼亚
监管名单      ：卡瑟尼亚是高风险辖区      ← 这份也完全不提"星海"
```

后两份文档跟问题**零词面重叠**，检索器看不见它们。

实测验证了这一点：

```
k=1    k=3    k=5    k=10   k=20
17%    32%    32%    43%    50%     ← 放大 20 倍，涨 33 分就不动了
```

**这不是调参能解决的，是范式本身的天花板。**

### 做法

不"找"，改成"走"：

1. **实体链接**——从问题里认出"星海亚洲机会基金"这个实体
2. **意图判断**——问题里有"关联""风险"，判定为风险穿透类
3. **沿关系走**——从基金出发，顺着 管理人→董事→关联公司→注册地→风险等级 走下去
4. **回溯证据**——走过的每条边都记着它出自哪份文档，路径本身就是证据清单

### 结果

| 题型 | BM25 | 图检索 |
|---|---|---|
| 四跳风险穿透 | 45.0% | **90.0%** |
| 共同董事 | 31.2% | **93.8%** |
| 聚合计数 | 37.5% | **92.3%** |
| 纯语义 | 22.8% | **0.0%** ← 注意这个 |

### 这一步真正的收获

图检索在纯语义题上是 **0%**，因为问题里没有实体名 = 没有起点。
**每种检索方式都有明确的能力边界。** 这直接引出了下一步。

---

## 第 4 步：混合 vs 路由（推翻了一个常识）

### 我本来以为的

把 BM25、向量、图三路结果用 RRF 融合，取长补短，肯定更好。

**这是业界的默认做法。** 我也是这么做的。

### 实测发现

```
              图检索    等权 RRF 融合     变化
聚合计数       92.3%  →    51.1%       -41 分
四跳风险穿透   90.0%  →    48.3%       -42 分
```

**融合反而把分数拉垮了。**

### 为什么

RRF 只看**名次**，不看"这一路在这类问题上到底可不可信"。

问"哪些公司和 A 有共同董事"，BM25 会返回一堆提到 A 的文档——
排名很高，但全是噪音。等权融合时，这些噪音和图检索的精确结果同等对待，
把真正的证据挤出了 top-10。

### 改法：路由，不是融合

先判断这个问题**该问谁**，再让主路优先出结果，剩余名额才给备选：

```
问题里没有实体名                → 走词面/向量（图没有起点）
问题里有"共同董事""关联""穿透"   → 走图
问题问"几只""哪些"+关系词        → 走图（聚合类 top-k 天然答不全）
其余                            → 走词面/向量
```

### 结果

| | 总计 recall@10 |
|---|---|
| 等权 RRF 融合 | 73.3% |
| **查询路由** | **86.3%** |

### 这一步真正的收获

> **正确做法不是"都要，加起来"，而是先判断这个问题该问谁。**

大多数 RAG 实现直接 top-k 一把梭，跳过了路由这一步。
**这是整个项目最值钱的一个结论**，因为它推翻了一个默认假设，而且有数字支撑。

---

## 第 5 步：那些"数字对了但其实错了"的坑

这一节是我认为面试最该讲的部分——**因为它们只有真跑才会暴露**。

### 坑 1：图检索一开始跑输了 BM25

图检索明明知道那条路径，分数却比 BM25 还低。

查下来不是图的问题，是**我的评测框架不公平**：
图检索把一份文档的 3.3 个块全吐出来，top-10 只覆盖 3 份文档；
而 BM25 的 10 个块散落在 10 份不同文档里。**同样的 k，预算差三倍。**

改成按文档轮转发放预算后才可比。

> 教训：**比较两个方案之前，先确认它们在同一量纲上。**

### 坑 2：遍历穿过了字面量节点

某次看路径可视化，发现是这样走的：

```
基金A -[最低认购额]-> "25万新元" <-[最低认购额]- 基金B -> ...
```

**两只基金因为最低认购额数字相同，就被判定为有关联。**

字面量（金额、日期、风险等级）是**属性值**，不是实体。
数值相同不构成任何关系。它可以是路径终点，绝不能是中转站。

修完：四跳题 78.6% → **90.0%**。

### 坑 3：枢纽节点

同理，辖区节点的度数是 17~25，托管银行是 14，而基金只有 5。

允许穿透枢纽，"共用一家托管行的两只基金"就会被判定为有关联——
这是关系图谱里**最常见的假阳性来源**。

禁止枢纽做中转（可以做终点）后：58.9% → **90.0%**，值 31 分。

### 坑 4：内存里对、落盘后错

同一条事实被多份文档支撑时，额外来源记在 `_extra_docs` 里。
但它不是正式字段，序列化时被 `asdict()` **静默丢弃**了。

内存里跑没问题，存盘再读就少了一批证据文档。**不报错，只是分数莫名其妙地低。**

修完：抽取图 67.2% → **73.6%**。

> 教训：这类 bug 读代码读不出来，只能靠"数字不对劲 → 打诊断 → 定位"。

## 第 6 步：实体消歧（最曲折的一段）

### 问题

同一家公司在不同文档里写法不同：

```
星海资产管理有限公司  /  星海资管  /  Starsea Asset Management Pte. Ltd.
```

不归并，图里就是三个孤立节点，**所有跨文档的多跳查询全部失效**。

### 弯路 1：只用向量 → 灾难性错合并

```
[向量 1.00] Daiyu Capital Management Ltd. == Dixing Capital Management Ltd.
[向量 1.00] Daiyu Capital Management Ltd. == Heming Financial Services Ltd.
```

相似度 **1.00**，却是毫不相干的三家公司。

原因：`bge-small-zh` 是**中文**模型，对纯英文串的表示几乎坍缩到同一点。
只看向量，所有英文公司名会被并成一个节点，**整张图作废**。

> **单一信号永远不足以触发合并。**

改法：词面判定作为守卫，向量说"像"还不够，词面也得说得通。拦下了 446 对。

### 弯路 2：词面只当守卫，不当证据 → 什么都没合并

加了守卫之后，消歧合并数变成 **0**。

因为"星海资管"和"星海资产管理有限公司"虽然词面明显匹配，
但向量相似度落在灰区，被送去排队等 LLM 裁决——没有 API key 就卡死了。

> **词面既是守卫，也是证据。** 强词面证据本身就该足以合并。

改成三值判定（strong / weak / incompatible）后，18 对中文简称正确合并。

### 弯路 3：跨文种靠 LLM → 调用 228 次只合并 1 对

中文名和罗马化名之间没有任何廉价信号，我用"共享邻居"做分块，
把候选对送 LLM 裁决。结果：

```
{"same": false, "reason": "中文名「柏观」与罗马化名「Jinyue」不对应"}
{"same": false, "reason": "「洄川国际控股」与「Daiyu Financial」不对应"}
```

**模型判断是对的，是我的分块根本没把正确的对配出来。**
共享辖区这种信号太弱，生成的几乎全是错误候选。

缺的信号其实非常显然：**拼音**。

```
岱屿 → daiyu，而 "Daiyu Financial Services Ltd." 的首个 token 就是 daiyu
```

`pypinyin` 是纯 Python、3.5MB、完全离线的确定性库。

> **有确定性方法可用时，不要让 LLM 去做它。**
> 228 次 LLM 调用 + 几乎全错的候选，被一个离线库替代了。

### 弯路 4：只比品牌拼音 → 传递性错合并

加了拼音，消歧欠账从 1.27 降到 1.04，**但 F1 反而从 80.1% 掉到 70.6%**。

查下来：

```
「Daiyu Capital Management Ltd.」的别名里混进了三家不同公司：
   岱屿资本管理有限公司
   岱屿金融服务有限公司
   岱屿环球投资有限公司
```

我的拼音规则**只比品牌**（岱屿 → daiyu），
于是同品牌的三家公司对上任何 `Daiyu * Ltd.` 都判"相同"。
然后并查集**传递性地**把它们全并成一坨。

两个修法：

1. **跨文种比对必须连业务类型后缀一起比**
   品牌是音译（岱屿→Daiyu），后缀是意译（资本管理→Capital Management），
   两部分都得对上。
2. **cannot-link 约束**——合并前检查两个簇里是否存在已知"明确不同"的成员对，
   有就拒绝合并。这是约束聚类里的标准做法，能拦住传递性扩散。

### 最终结果

| 版本 | F1 | 消歧欠账 |
|---|---|---|
| 只用向量 | 崩溃（错合并） | — |
| 加词面守卫 | 80.1% | 1.27 |
| 加拼音（只比品牌） | 70.6% ↓ | 1.04 |
| **加后缀 + cannot-link** | **81.6%** | **1.15** |

注意第三行：**欠账降了，分数反而掉了**——因为合并得多不等于合并得对。

## 第 7 步：Prompt 工程（三个真实发现）

### 发现 1：不给 schema，输出契约会漂移

v1 prompt 只说"抽取三元组，以 JSON 输出"。
结果：326 份文档，**每次都产出合法 JSON，但结构在 6 种形态间随机跳**：

```
568 次  {"entities": ..., "relations": ...}
357 次  {"实体关系三元组": ...}
 36 次  {"实体关系": ...}
  9 次  {"entity_relations": ...}
```

**不是模型能力不行，是没有稳定契约，下游根本没法写解析器。**
976 次重试全是白花的钱。

加上封闭 schema（实体类型枚举 + 关系白名单 + 输出格式）后：
**解析重试 0 次，325 份失败变成 0 份失败。**

### 发现 2：约束过头会压制合法行为

v3 prompt 写着"**只抽文档明确写出的事实，不推理、不补全**"。

结果监管观察名单整份被跳过，12 条辖区风险等级一条没抽出来。

因为名单长这样：

```
一、高风险管辖区
　　　· 维兰群岛
　　　· 卡瑟尼亚
```

**没有任何一句话写着"维兰群岛的风险等级是高风险"**——需要读懂排版结构。

模型是对的，**是我的 prompt 把"解读结构"和"凭空推理"混为一谈了。**

v4 把约束细化成"不许臆测，但必须读懂文档结构"，并补了一个结构型文档的正例：

```
RISK_LEVEL recall:  0%  →  100%
整体 F1:          78.5% → 80.1%
```

> 这正是 prompt 文件里 `hypothesis` 字段存在的意义——
> **改 prompt 之前先写下预期，跑完再对照。**
> 我当初的预期是"负例能压制假阳性"，完全没料到它同时压制了合法的结构化解读。
> **预期错了，比分数没涨更有信息量。**

### 发现 3：两个设计决策打架

v4 抽出的 12 条全被 evidence 回查拦下，显示"100% 幻觉率"。

这是**误报**：prompt 里我让模型写 `一、高风险管辖区 · 维兰群岛`
这种"标题+列表项"的组合式证据，而回查要求逐字连续出现在原文——
这个串在原文里并不连续存在。

修法是原则性的：**evidence 可以由多个片段组成，但每个片段都必须逐字出自原文。**
写了 6 条回归测试确认反幻觉能力没被削弱（编造的片段照样拦下）。

## 最终结果汇总

### 检索（recall@10）

| 方案 | 总计 |
|---|---|
| BM25 基线 | 65.2% |
| + 向量 | 70.5% |
| + 图检索（等权 RRF 融合） | 73.3% |
| **+ 图检索（查询路由）** | **86.3%** |

### 抽取（LLM，DeepSeek）

| prompt 版本 | precision | recall | F1 | 解析重试 |
|---|---|---|---|---|
| v1 无约束 | 0% | 0% | 0% | 976 次 |
| v3 schema + few-shot | 88.1% | 70.8% | 78.5% | 0 |
| **v4 + 结构化正例** | **88.0%** | **76.0%** | **81.6%** | **0** |

### 各组件的分值贡献

| 组件 | 值多少分 | 证据 |
|---|---|---|
| 上下文切块 | 单跳 recall@1 58%→100% | A 组对比 |
| 向量检索 | 纯语义 22.8%→63.6% | B 组对比 |
| 图检索 | 四跳 45%→90% | B 组对比 |
| 枢纽阻断 | 四跳 58.9%→90% | 消融行 |
| 查询路由（vs 融合） | 总计 73.3%→86.3% | 消融行 |
| 拼音消歧 | LLM 调用 228→82，F1 +11 分 | 抽取报告 |
| schema 约束 | 解析失败 325→0 份 | prompt A/B |
| 结构化正例 | RISK_LEVEL 0%→100% | prompt A/B |

## 如果要继续优化，下一步做什么

| 方向 | 预期收益 | 理由 |
|---|---|---|
| 加 cross-encoder 重排 | 纯语义 63.6% → 约 75% | 目前召回靠单一向量模型，重排能显著提精度 |
| 路由粒度细化 | 两跳题 70.2% → 约 82% | 实测两跳题上"融合"优于"路由"，说明该按题型给权重而非一刀切 |
| 跨文种消歧补齐 | 抽取图 78.2% → 接近 86.3% | 还有 9 个实体未合并，差距就在这 |
| 抽取用更强的模型 | recall 76% → ? | 目前 recall 是瓶颈（precision 已 88%） |

**注意最后一行**：precision 88% 而 recall 76%，说明**模型抽得准但抽得不全**。
优化方向应该是"让它抽更多"，而不是"让它抽更准"。
