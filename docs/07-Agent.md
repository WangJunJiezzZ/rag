# Agent：让模型自己编排工具，到底好多少、贵多少

> 这一章回答一个问题：**把固定的 RAG 流水线换成 Agent（让模型自己决定调哪些工具、调几次），在同一套评测集上值不值得？**
>
> 所有数字都来自 109 道题的实测。标注、判分和局限性都如实写明。
>
> **只想知道结论和怎么讲给别人听：** 读第零节和第七节（面试问答）就够了。
>
> 本章结构：是什么（第零节）→ 怎么做的（第一节）→ 结果与失败分析（第二、三节）→ 判分（第四节）→ 怎么用（第五节）→ 怎么一步步变准的（第六节）→ 问答（第七节）。

---

## 零、白话版

### 两种做法

| | 固定流水线（原来的 RAG） | Agent |
|---|---|---|
| 怎么工作 | 流程写死：判断走哪条检索路 → 一次性取回 8 段资料 → 让模型写答案 | 模型手里有 7 个工具（查角色、查关系、全文检索、读原文……），**自己决定**查什么、查几次、什么时候停 |
| 调用模型 | 1 次 | 平均 3.6 次 |
| 类比 | 按清单去图书馆借 8 本书，借完就开始写 | 边查边想，这本没有就换一本，查到线索再顺着往下查 |

Agent 的工具就是第六章做的 MCP Server，两个项目用的是同一套工具。

### 结论（109 题，自动抽取的图谱）

| | 固定流水线 | Agent |
|---|---|---|
| **答对率** | 88.1%（96/109） | **97.2%**（106/109） |
| 可答题误拒答率 | 13.4% | **1.0%** |
| 陷阱题正确拒答 | 100% | 100% |
| 每题 token | 约 1,000 | 约 13,500（**13 倍**） |
| 109 题总花费（估算） | $0.038 | $0.471（**12 倍**） |

**一句话：Agent 多答对了 10 道题，代价是 12 倍的成本；提升全部来自需要多步推理的题，简单题两边打平。**

所以实际应用中的合理做法是**分流**：简单题走便宜的固定流水线，多跳、列举、语义模糊的题才交给 Agent。

### 怎么用

- **看结果（不用装任何东西）：** 打开线上的[回放页面](https://wangjunjiezzz.github.io/rag/agent.html)。顶部是 109 题的评测结果，下面的列表里点任意一题，就能看到两种方式的逐步回放
- **在本地复现数字（不花钱）：** `python run.py eval-agent -- --split test`，默认只读缓存
- **自己问一个新问题（花钱，每题约 $0.005）：** `python run.py mcp-chat -- -q "你的问题"`

完整命令见第五节。

## 一、怎么做的

### Agent 是怎么实现的

Agent 的核心是一个**循环**，代码在 [`mcp_app/client.py`](../src/graphrag/mcp_app/client.py) 的 `MCPChat.ask()`，不到 50 行：

```
准备：连上 MCP Server → 拿到 7 个工具的定义 → 读取图谱 schema 放进 system prompt

第 1 轮：把「system prompt + 问题 + 工具定义」发给 DeepSeek
          │
          ├─ 模型说「我要调工具」（返回 tool_calls，可以一次调多个）
          │     → 通过 MCP 逐个调用工具
          │     → 把每个工具的结果作为 role=tool 消息追加到对话里
          │     → 进入下一轮，把**完整的对话历史**再发给模型
          │
          └─ 模型不再调工具，直接给出文字回答 → 结束

保护：最多 8 轮（max_steps），到了还没答完就停止
```

几个关键设计：

| 设计 | 做法 | 为什么 |
|---|---|---|
| 工具从哪来 | 全部来自第六章的 MCP Server，Agent 这边**一个工具都不自己实现** | 同一套工具，命令行、回放页面、评测脚本都能复用；也能换成任何别的 MCP 客户端 |
| 模型怎么知道有哪些关系 | 开始前读取 `graphrag://schema` 这个 resource，放进 system prompt | 省掉模型"先调个工具问问有哪些关系"的一轮 |
| 怎么防编造 | system prompt 要求"只依据工具返回的内容作答，查不到就说未找到依据，不要用你对这部动画的记忆" | 喜羊羊很有名，DeepSeek 自己就记得很多剧情 |
| 怎么引用证据 | 要求回答末尾写"依据: doc-xxxx" | 评测时据此统计引用是否落在标准证据里 |
| 工具出错怎么办 | 参数错误、找不到实体，都作为工具结果回给模型，不抛异常 | 模型读得懂提示，会自己换个写法重试 |
| 怎么可复现 | 每一轮的请求按完整输入缓存；跨平台时用稳定键兜底 | 别人拿到仓库不用 key 也能离线复现全部数字 |

评测时不走命令行，而是在进程内直接连 MCP Server（[`eval/agent.py`](../src/graphrag/eval/agent.py)），4 道题并发跑。请求内容与 `mcp-chat` 完全一致，所以手动跑过的题可以直接命中缓存。

### 怎么保证对比是公平的

| 约束 | 做法 |
|---|---|
| 同一个模型 | 两边都是 deepseek-chat，temperature=0 |
| 同一份图谱 | 都用自动抽取的图谱（`data/index/extracted_graph.json`） |
| 同一套判分 | 同一个判分函数；关系类题用同一个 LLM 判官（见第四节） |
| 同一个成本口径 | 都按 token × 同一张价目表估算。缓存命中时实际花费为 0，但比的是"这套方法要花多少"，所以一律按 token 折算 |
| 只比共同的题 | 只统计两边都跑出结果的题，避免缓存缺口伪装成分数差 |

**没有控制的变量：** 两边的提示词不同。固定流水线用的是防幻觉版 `answer/v3_guarded`，Agent 用的是 `mcp_app/client.py` 里的 system prompt。这是两种方法本身的一部分，没法做到完全一样。

## 二、结果

### 按划分

| 划分 | 题数 | 固定流水线 | Agent |
|---|---|---|---|
| train | 45 | 84% | 96% |
| dev | 23 | 91% | 96% |
| test | 41 | 90% | **100%** |

三个划分的趋势一致。test 上没有三跳题、关系路径题也只有 1 道，所以最终报的是**全部 109 题**，同时列出各划分的数字。

### 按题型（答对题数）

| 题型 | 题数 | 固定流水线 | Agent | 差 |
|---|---|---|---|---|
| 单跳事实 | 18 | 18 | 18 | 0 |
| 同义改写 | 16 | 16 | 16 | 0 |
| 易混实体 | 12 | 12 | 12 | 0 |
| 幻觉陷阱 | 12 | 12 | 12 | 0 |
| **两跳关系** | 20 | 16 | **20** | +4 |
| **纯语义** | 12 | 8 | **10** | +2 |
| **列举比较** | 9 | 7 | **9** | +2 |
| 三跳关系 | 5 | 4 | 5 | +1 |
| 关系路径 | 5 | 3 | 4 | +1 |

**陷阱题值得单独说。** 这套语料是《喜羊羊》《铁甲小宝》，DeepSeek 自己就"记得"很多剧情。陷阱题问的是语料里没有的内容，比如"卡布达有多重"，Agent 12 道全部正确拒答，没有拿自己的记忆来编答案。

### 两边结论不同的 12 道题

**Agent 对、流水线错（11 道）**，有三种典型情况：

| 情况 | 例子 | 说明 |
|---|---|---|
| 证据被挤出检索名额 | q-0082 卡布达搭档的爷爷封印过哪个机器人 | 抽取图多出一条错误边，带进来的文档把关键原文挤出了 8 个名额（详见 [06-MCP 案例一](06-MCP.md)） |
| 需要跨文档推算 | q-0069 小灰灰是武大狼的第几代孙 | 没有任何文档写"251"。Agent 读了三份档案，按 249 → 250 → 251 推出来；流水线拒答 |
| 要继续往下查 | q-0063 小灰灰的妈妈用什么打爸爸 | 流水线只拿到了"妈妈是红太狼"，Agent 又去查了红太狼的武器 |

**流水线对、Agent 错（1 道）：q-0052"哪位角色负责管理整片草原？"**
Agent 的检索词是"管理整片草原 **村长**"：**它自己往检索词里加了"村长"**，等于先预设了答案，结果被引向慢羊羊（羊村村长）。写着"包包大人……青青草原的管理者"的 doc-0009 根本没有出现。用原问题直接检索，doc-0009 排第一。

### 两边都错的 2 道

| 题目 | Agent 的失败方式 | 根因 |
|---|---|---|
| q-0058 哪个机器人贪杯好饮 | 调用 **27 次**工具、达到 8 轮上限，没有给出答案 | **其实只差一步**（见下方逐轮经过） |
| q-0088 藏之助和卡布达有什么联系 | 回答"没有直接关系" | 答案是"同属正义阵营"，要比较两个角色的**属性**。工具只能沿关系走，而阵营这类字面量节点按设计不能作为中转 |

**q-0058 的逐轮经过**（在回放页面上核对轨迹时发现，最初写的"没找到"是错的）：

| 轮次 | 做了什么 | 结果 |
|---|---|---|
| 1～2 | 检索 4 次，检索词里有"爱喝酒""喜欢喝酒" | 每个检索词都带了**"机器人"这个泛词**，结果被"阵营一览"等提到大量机器人的文档占满 |
| 3～6 | 挨个查询各个机器人的邻居 | 没找到 |
| 7 | 去掉泛词，只搜"贪杯好饮" | **第 3 条就是蝎子莱莱**，摘要写着"该角色爱喝酒" |
| 8 | 去读这份原文 | 这是最后一轮：读到的内容**还没交回给模型就达到了上限，已拿到的证据被整个丢掉** |

所以它暴露的是两个问题：检索词带泛词；以及 Client 的设计缺陷——**步数用完时，应该强制模型根据已有信息作答，而不是什么都不返回**。

### 成本去哪了

Agent 平均每题 4.5 次工具调用、3.6 次模型调用。**每一轮都要把之前所有的工具结果重新发给模型**，所以 token 随轮数增长得比线性还快。最贵的几道：

| 题目 | 工具调用 | token |
|---|---|---|
| q-0058 贪杯好饮（没答出来） | 27 | 51,495 |
| q-0056 讲话又臭又长 | 15 | 41,247 |
| q-0092 正义阵营有哪些机器人 | 13 | 22,780 |
| q-0093 带编号的机器人有几台 | 16 | 21,502 |

后两道是列举题：工具里没有"按属性列出所有角色"，Agent 只能一个个查。**缺一个合适的工具，成本就会翻好几倍。**

## 三、失败类型汇总（这是改进的依据）

| 类型 | 例子 | 可能的改进 | 状态 |
|---|---|---|---|
| 工具缺失：不能按属性比较或列举 | q-0088、列举题成本高 | 加一个"按关系 / 属性列出实体"的工具 | 未做 |
| 步数用完时丢弃已拿到的证据 | q-0058 第 8 轮读到了答案 | 最后一轮不再提供工具，强制模型根据已有信息作答 | 未做 |
| 检索词带泛词 | q-0058 前 4 次检索都带"机器人" | 提示模型：检索词只写区分性的特征，不写"机器人""角色"这类泛词 | 未做 |
| 检索时预设了答案 | q-0052 检索词里自己加了"村长" | 提示模型：第一次检索用原问题的措辞，不要掺入自己猜的答案 | 未做 |

每一项改动都会改变工具定义或提示词，之前的 Agent 缓存会全部失效，需要重新跑，全量约 $0.5。

## 四、判分：为什么要引入 LLM 判官

### 问题：关键词判分对关系类题会放水

原来的判分规则是"标准答案里的实体都出现在回答中就算对"。对单跳事实题够用，对关系类题会系统性放水：**回答把中间人的名字都列出来了，结论却是"无法确定"，照样判对。**

人工核对 41 条多跳回答，发现 3 例：

| 题目 | 回答 | 关键词判分 |
|---|---|---|
| q-0062 小灰灰的外婆是谁 | 写了"按此路径应为娘娘狼"，**结论却是"无法回答"** | ✓（错判） |
| q-0087 小让和鲨鱼辣椒有什么关系 | 关键词都在，结论是"无法断定二者存在何种关系" | ✓（错判） |
| q-0088 藏之助和卡布达有什么联系 | 结论是"没有直接关系"，漏了"同属正义阵营" | ✓（错判） |

只收紧关键词是**治标不治本**：给 q-0087 加上"封印"之后，那条回答仍然两个词都包含，照样判对。

### 做法：LLM 判官 + 标注集校准

- **范围：** 只接管两跳、三跳、关系路径三类可答题，共 30 道；其余题型仍用关键词判分
- **判官：** DeepSeek，按 [`prompts/judge/v2_rubric.md`](../prompts/judge/v2_rubric.md) 的规则判断"**最终结论**是否与标准答案一致"。判官的输出也进缓存，同一条回答永远得到同一个判定
- **校准：** 标注集 [`data/eval/judge_labels.jsonl`](../data/eval/judge_labels.jsonl) 共 60 条，每条绑定一条具体的回答全文

| 判官版本 | 校准集（写规则时见过） | 留出集（写完规则后才出现） |
|---|---|---|
| 关键词判分 | — | — （60 条整体一致率 95.0%） |
| v1 | 41/41 | **18/19（94.7%）** |
| v2 | 41/41 | 19/19 |

**v1 在留出集上误判了一条：q-0085。** Agent 的回答开头说"没有**直接**关系"，随后推出了正确的姻亲关系链，v1 却判错。原因是规则 3 把"没有直接关系"和"无法确定"放在了一起，一律算错。v2 把两者区分开，并确认没有反过来放宽：q-0087 和 q-0088 那两条"没有直接关系、只列零散事实"的回答，仍然判错。

**必须如实说明的三点：**
1. **v2 是看过留出集之后改的**，所以它的 19/19 不是样本外成绩。可以报告的样本外成绩是 **v1 的 94.7%**
2. **60 条标注都是 Claude 标的**，标注文件里记录了 `labeler: claude`、`human_reviewed: false`。在有人工复核之前，不能称之为"人工标注"
3. **判官和被评测的 Agent 都是 DeepSeek**，可能存在偏向自己风格的问题。校准集能部分检验这一点，但不能完全排除

### 判官对结果的影响

| | 关键词判分 | LLM 判官 |
|---|---|---|
| 固定流水线 | 89.9% | 88.1% |
| Agent | 97.2% | 97.2% |

关键词判分**高估了固定流水线**，因为流水线更常出现"列出证据、结论却拒答"的回答，这正是关键词判分放水的地方。

## 五、怎么跑

```bash
source .venv/bin/activate          # Windows: .\.venv\Scripts\Activate.ps1

# 默认只读缓存，不联网、不花钱。这些题都已缓存，可以直接复现上面的数字
python run.py eval-agent -- --split test
python run.py eval-agent -- --split train
python run.py eval-agent -- --split dev

# 校准判官（默认只读缓存）
python run.py calibrate-judge
python run.py calibrate-judge -- --prompt judge/v1_rubric    # 看 v1 在留出集上的误判
```

加 `--online` 才会调用 DeepSeek。联网前会打印预估花费，**实际花费**超过 `--max-usd`（默认 $0.5）就不再开新题；缓存命中不计入。

**线上查看：** 回放页面 `agent.html` 顶部就是 109 题的评测结果。两边结论不同或都答错的 14 道题，点一下就能看到逐步回放；也可以用 `agent.html#q-0058` 这样的链接直接打开某一道题。回放由 `python run.py build-static` 从缓存离线生成，页面本身不调用任何模型。

输出：
- `reports/phase4_agent_{train,dev,test}.json`：逐题的答案、判分、工具序列和 token
- `reports/judge_calibration_v{1,2}_rubric.json`：判官校准结果

代码：

| 文件 | 作用 |
|---|---|
| [`src/graphrag/eval/agent.py`](../src/graphrag/eval/agent.py) | 两边的运行器：Agent 走进程内 MCP，与 `mcp-chat` 请求逐字节一致；流水线从端到端评测缓存重放 |
| [`src/graphrag/eval/judge.py`](../src/graphrag/eval/judge.py) | LLM 判官 |
| [`scripts/eval_agent.py`](../scripts/eval_agent.py) | 对比报告 |
| [`scripts/calibrate_judge.py`](../scripts/calibrate_judge.py) | 判官校准，按校准集 / 留出集分别报告 |

## 六、怎么一步步变准的

### 评测的演进过程（按时间顺序）

这一章的数字不是一次跑出来的。评测本身改了好几轮，**每一轮都让数字变得更可信，而不是更好看**：

| 步骤 | 发现了什么 | 怎么改的 | 对数字的影响 |
|---|---|---|---|
| 1. dev 小批量先跑 | 23 题，Agent 23/23 全对 | 不急着下结论，先逐条人工核对 | — |
| 2. 人工核对 | Agent 有 1 题其实答错了（q-0088），却被判对；流水线也是 | 定位到关键词判分只查了一个名字 | 两边各减 1 题 |
| 3. 排查判分器 | 回答里的"[8]""doc-0018"会命中数字答案 | 判分前去掉引用标记 | 已有分数无变化，属于潜在隐患 |
| 4. 收紧关键词 | 给 q-0087、q-0088 加上关系本身的关键词 | 改评测集，重算所有历史数字 | 流水线 v3 可答题 89.7% → 88.7% |
| 5. 发现收紧不够 | q-0087 收紧后仍被判对 | 关系类题改用 LLM 判官 | — |
| 6. 判官 v1 | 校准集 41/41 | 不采信，等新数据检验 | — |
| 7. 留出集检验 | v1 在 19 条新回答上误判 1 条（q-0085） | 修正规则 3，做成 v2，60/60 | test 上 Agent 98% → 100% |
| 8. 跑全量 | 花费上限按估算值算，全缓存时也会"超支"并静默跳题 | 改为按实际 API 花费 | 修复前某次结果虚高到 100% vs 100% |
| 9. 做回放页面 | 逐轮核对轨迹，发现两道失败题的归因都写错了 | 按实际轨迹重写失败分析 | q-0058 从"没找到"改为"找到了但步数用完"；q-0052 从"被图谱带偏"改为"检索时预设了答案" |
| 10. 跨平台 | Linux 上用到全文检索的 Agent 回放第 2 轮就对不上缓存 | chat 加稳定键兜底 | Linux 上复现出相同数字 |

### 踩过的坑（都是实测发现的）

1. **判分会被引用编号干扰。** 标准答案是数字的题（如"8""10"），回答里的"[8]"或"doc-0018"会被当成答中。修复时核对过：固定流水线两份图谱各 109 题，判分结果一道都没变，属于潜在隐患
2. **判分规则的例子泄露了答案。** 判官规则里写同义词例子时，第一版用了"表亲 / 远房表亲"，正是校准集里 q-0084 的原话。这样校准出来的一致率会虚高，已换成数据集里没有的例子
3. **提示词模板把 JSON 花括号当成了占位符。** 模板用 `str.format()` 渲染，示例里的 `{"verdict": ...}` 会报错，必须写成 `{{ }}`
4. **花费上限算错了口径。** 第一版按 token 估算值来判断是否超限，即使全部命中缓存、实际一分钱没花，累计几道题后也会"超限"，把后面的题**静默跳过**。表现为分数突然变得很好看，而且共同题数变少了。已改为只按实际 API 花费计算
5. **总的一致率会掩盖问题。** v1 的总一致率 98.3% 过了 95% 的门槛，但留出集只有 94.7%。必须分开报告

**共同的教训：评测代码本身也要被评测。** 这五个问题都不会报错，只会让数字悄悄失真，而且大多数是让结果**变得更好看**。

## 七、面试问答

> 前两题是最基础的，一定会被问到。

### Q0-1：用一句话说，Agent 是什么？和 RAG 是什么关系？

> Agent 就是让模型自己决定下一步做什么：调哪个工具、调几次、什么时候停。RAG 是"先检索、再生成"的固定流程。
> 两者不是对立的：我的 Agent 手里的工具就包括检索，区别在于检索什么、检索几次，由模型根据中间结果决定，而不是写死在流程里。

### Q0-2：你的 Agent 是怎么实现的？

> 核心是一个不到 50 行的循环。把问题和 7 个工具的定义发给 DeepSeek；它如果要调工具，我通过 MCP 去调，把结果追加到对话里再发回去；它不再调工具时就结束，最多 8 轮。
> 工具全部来自我自己写的 MCP Server，Agent 这边一个工具都没自己实现。另外做了三件事：工具出错时把提示回给模型让它自己改；要求回答末尾标注依据的文档；每一轮都按完整输入缓存，所以评测可以离线复现。

### Q1：Agent 比 RAG 好吗？

> 要看题目。我在 109 道题上做了对比，同一个模型、同一份图谱、同一套判分。Agent 答对率从 88.1% 提到 97.2%，但成本是 12 倍。
> 简单题两边都是满分，提升全部来自两跳、列举、语义模糊这类需要多步推理的题。所以我的结论是**分流**：简单题走固定流水线，复杂题才上 Agent。

### Q2：Agent 具体强在哪？

> 强在能**根据中间结果决定下一步**。固定流水线一次性取回 8 段资料，取漏了就没有机会补。
> 最典型的是一道三跳题：抽取图里多出一条错误的边，带进来的文档把关键原文挤出了检索名额，流水线只能拒答。Agent 查到第二跳之后自己决定再查一步，就拿到了那份原文。
> 还有一道题要跨三份档案推算代数，没有任何文档直接写出答案，流水线拒答，Agent 推出来了。

### Q3：Agent 会犯什么错？

> 我做了逐题的失败分析，主要有四类：工具缺失，比如不能按属性比较或列举；检索词带泛词，前 4 次检索都加了"机器人"，结果被无关文档占满；步数用完时丢弃已拿到的证据，有一道题第 8 轮已经读到了答案，却因为达到上限什么都没返回；还有检索时预设答案，问"谁管理整片草原"，它在检索词里自己加了"村长"，被引向了错误的人。
> 两道语义题的失败，归根到底都是**检索词写得不好**，而不是工具不够。
> 而且这两道题我一开始的归因都是错的：一道我以为"没找到"，一道我以为"找到了却被带偏"。后来在回放页面上逐轮核对轨迹才纠正过来。**只看最终答案，会得出错误的失败归因**，这也是我做回放页面的原因。

### Q4：你怎么知道判分是准的？

> 一开始用的是关键词判分，我人工核对多跳题的回答时发现它会放水：回答里提到了关键人名，结论却是"无法确定"，照样判对。
> 所以我对关系类题引入了 LLM 判官，并用标注集校准，**校准集和留出集分开报告**。第一版在留出集上是 94.7%，误判了一条，原因是我写的规则把"没有直接关系"一律当成错。改规则之后 60 条全部一致，但我会说明：第二版是看过留出集才改的，它的成绩不算样本外。
> 引入判官后，固定流水线的分数从 89.9% 降到 88.1%，说明关键词判分之前高估了它。

### Q5：12 倍的成本怎么降？

> 三个方向，都是从失败分析里来的。第一是分流，只把复杂题交给 Agent。第二是补工具：列举题要一个个去查，是因为缺少"按属性列出所有角色"的工具，补上之后调用次数应该能降下来。第三是提前停止：连续几轮没有新信息就收尾。
> 这些我还没做，因为每次改工具定义都要重跑全量评测，我想先把基线数字定下来。

### Q6：怎么保证结果可复现？

> 所有模型调用都按完整输入做缓存，包括每一轮的消息历史和工具定义。只要工具是确定性的，Agent 的整条调用轨迹都能从缓存逐轮回放。判官的输出也进缓存。
> 所以别人拿到仓库，不需要 API key，就能离线复现这一章的所有数字。

## 八、局限性

- **规模小：** 109 道题、42 份文档，而且文档是模板化的。换到真实文本，两边的分数都会下降，差距也可能变化
- **只跑了一次：** temperature=0，没有做多次采样，也没有报置信区间。差 10 道题在 109 道里是有意义的，但单个题型的差异（比如关系路径 3 vs 4）不能单独下结论
- **只测了抽取图谱：** 标准图谱上还没有跑 Agent
- **标注未经人工复核：** 见第四节
- **成本是估算值：** 按 deepseek-chat 的近似单价计算，只作量级参考
