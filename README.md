# graphrag-lab

一个**可评测、可消融**的 GraphRAG 参考实现。

不是"跑通一个 RAG demo"，而是回答一个更具体的问题：

> **纯向量 RAG 在什么情况下会失败？加上什么能把分数拉回来？每一步各值多少分？**

全部结论以评测数字给出。题材是《喜羊羊与灰太狼》和《铁甲小宝》两部动画的角色关系——
"小灰灰的爷爷是谁""灰太狼的表哥是谁""小让的爷爷封印过哪个机器人"。
事实取自维基百科等公开资料，译名统一用中国大陆播出版。

## 一、这个项目要证明的三件事

| # | 命题 | 验证方式 | 结果 |
|---|---|---|---|
| 1 | 纯检索对**多跳关系**效率低下：证据与问题零词面重叠，要靠堆 top-k 碰运气 | 同一批两跳题，比较图检索与 BM25 各要多大的 k 才能召回全部证据 | ✅ 图检索 k=5 即 100%；BM25 放大到 k=20 仍只有 82% |
| 2 | **检索指标好看不等于答案对**：按文档算的 recall 会掩盖块级缺失 | 两跳题检索 recall@8 = 100% 时看端到端答对率 | ✅ 首版答对率只有 25%，定位到"发出去的是每份档案的标题块"，修复后 85%～90% |
| 3 | **Prompt 对幻觉的抑制可被量化**，而非玄学 | 三版 answer prompt A/B，同时看答对率与拒答率 | ✅ 陷阱题拒答三版均 100%；最严的 v3 使误拒答 6.2% → 11.3%，**更强约束反而更差** |

## 二、数据集：先建图，再渲染文档

这是本项目最重要的设计决策。

真实世界是 `文档 → 抽取 → 图`。本项目**反着来**：

```
  角色关系图谱 (ground truth, 事实来自公开资料)
        │
        ├──► 渲染成角色档案、名册、剧情梗概  ──► 系统的输入
        │
        └──► 题库声明每题依赖哪几条边        ──► 标准答案 + 证据文档清单
```

**带来的好处**：题目是人写的，但「哪几份文档是证据」是从图里算出来的，不是人标的。
于是可以计算 **retrieval recall@k** —— 这个指标是整个项目的地基，
没有它，"我的检索变好了"就只是一句感想。题库引用了图里不存在的边会直接报错，
保证题库和图谱不会悄悄脱节。

```
实体 49（节目 2 / 角色 38 / 地点 4 / 团体 2 / 道具 3）   边 174   文档 42   总字数 12,815
评测集 109 题 / 9 种能力 / train 45 · dev 23 · test 41
```

### 刻意制造的四类难度

| 难度 | 做法 | 打击的环节 |
|---|---|---|
| **每条关系只写在一份文档里** | "小灰灰的父亲是灰太狼"只写在小灰灰的档案里，"灰太狼的父亲是黑太狼"只写在灰太狼的档案里 | 多跳检索：**没有任何一份文档同时提到小灰灰和黑太狼**。关系路径题两端从不共现，已由 `verify_dataset.py` 形式化验证 |
| **名字高度雷同** | 喜羊羊/美羊羊/懒羊羊、灰太狼/红太狼/蕉太狼/香太狼/灰二太太狼 | 向量检索与实体消歧：它们在向量空间里挨得极近 |
| **证据只写别名** | 剧情梗概里只写「高圆寺博士」、搭档关系里只写「藏之助」、居民登记里只写「慢羊羊村长」 | 实体消歧：不归并，图就断开。别名只在本人档案里声明一次（「又名……」） |
| **指代与列表** | 档案第二、三节全部用「该角色」指代；居民登记、阵营一览是「标题 + 列表项」格式 | 切块（孤儿 chunk）与抽取（读不懂排版就整份漏抽） |

> `python run.py verify` 会逐条验证上述断言（证据完整、答案可支撑、多跳不可短路、纯语义题零词面重叠、划分无泄漏）。

## 三、实测结果

复现：`python run.py retrieval -- --with-extracted`

### A 组　切块策略（recall@1，检索器固定 BM25）

| 题型 | fixed | section | **contextual** |
|---|---|---|---|
| 单跳事实（原词） | 88.9% | 66.7% | **77.8%** |
| 单跳事实（同义改写） | 50.0% | 37.5% | **68.8%** |
| 易混角色 / 别名 | 87.5% | 58.3% | **87.5%** |
| 总计 | 56.4% | 43.2% | **57.1%** |

**孤儿 chunk 被复现并修复。** `section` 切出来的「三、人物关系　该角色的父亲是灰太狼」
不含角色名，recall@1 掉到 43.2%；补上「小灰灰 角色档案」前缀后回到 57.1%。

> `fixed` 总分与 `contextual` 接近，但机制不同：档案平均只有 300 字，比 350 字的窗口还短，
> `fixed` 基本是**一份文档一块**（50 块 vs 187 块），当然不会有孤儿。文档一长它就失效。
> **只看总分会得出错误结论。**

### B 组　检索路径消融（recall@10）

| 题型 | BM25 | Dense | Graph<br>(标准图) | Graph<br>无枢纽阻断 | RRF<br>三路等权 | Graph<br>(抽取图) | **Routed<br>路由** |
|---|---|---|---|---|---|---|---|
| 单跳事实（原词） | 100% | 100% | 100% | 100% | 100% | 100% | **100%** |
| 单跳事实（改写） | 93.8% | 100% | 81.2% | 87.5% | 93.8% | 81.2% | **100%** |
| 纯语义（无角色名） | 33.3% | 75.0% | 0.0% | 0.0% | 66.7% | 0.0% | **66.7%** |
| 易混角色 / 别名 | 100% | 95.8% | 100% | 100% | 100% | 100% | **95.8%** |
| 两跳关系 | 67.5% | 75.0% | **100%** | 100% | 97.5% | 100% | **100%** |
| 三跳关系 | 76.7% | 86.7% | **100%** | 93.3% | 93.3% | 100% | **100%** |
| **关系路径（招牌）** | 80.0% | 80.0% | **100%** | 90.0% | 90.0% | 100% | **100%** |
| 列举比较 | 90.0% | 85.6% | 72.2% | 72.2% | 93.3% | 72.2% | **90.0%** |
| **总计** | 80.9% | 88.2% | 82.0% | 82.1% | 92.9% | 82.0% | **94.4%** |

```
BM25 80.9%  →  +Dense 87.0%  →  +Graph +路由  94.4%
```

### 五条结论

**① 纯检索找多跳证据靠的是堆 k，图检索靠的是走**

```
两跳题 recall@k        k=1   k=3   k=5   k=10   k=20
  BM25                 40%   60%   62%    68%    82%    ← 放大 4 倍才从 62% 爬到 82%
  Graph(标准图)        42%   95%  100%   100%   100%
```
关键证据（祖父辈的档案、表哥妻子的档案）与问题**零词面重叠**。
语料只有 42 份，k=20 已经接近把半个语料库塞进上下文，BM25 仍然拿不全。

**② 检索 recall 100%，答对率却只有 25%——指标掩盖了块级缺失**

首版端到端评测里，两跳题的检索 recall 是 100%，答对率却只有 25%。
翻开上下文才发现：图检索按文档轮转发 chunk，每份档案**先发出去的是第一块**——
「小灰灰 角色档案 + 资料来源说明」这个标题块。写着"该角色的父亲是黑太狼"的那一块
根本没进上下文，模型只能如实回答"资料中未提及"。**recall 按文档算，只要文档里任意一块被召回就算命中。**

修复后两跳题答对率 25% → 85%～90%，端到端总答对率约 91%。三处修复：
- **关系链模板**：认出问题里的关系词（爷爷 → PARENT_OF/GRANDPARENT_OF，表哥 → COUSIN_OF），
  只沿这几种边走。否则从灰太狼出发一跳就连着 7 份文档，第二跳的香太狼档案排不进 top-8
- **文档内挑块**：优先发提到这条边两端名字的那一块（先抹掉节目名，不数档案主人自己的名字）
- **短前言并入第一节**：标题 + 资料说明不再单独成块

**③ 等权融合并不总是负收益，但路由仍然更好——前提是公平对照**

早期基金语料上测到过"等权 RRF 把聚合题从 92% 拉到 51%"。换成新语料后：

```
RRF(BM25+Graph)        89.7%    ← 少了向量这一路, 和路由比不公平
RRF(BM25+Dense+Graph)  92.9%    ← 三路都有, 只差"融合 vs 路由"
Routed                 94.4%    ← 关系路径 90% → 100%, 三跳 93.3% → 100%
```
**旧结论没有复现。** 这里得到的教训是另一件事：消融实验里最容易出错的是对照组，
一开始拿"两路融合"去比"三路路由"，差距有一半来自向量本身。

**④ 阻断枢纽节点：值多少分取决于查询模板**

两个节目节点各连着 15～16 个角色。允许穿透，同一部剧里任意两个角色都"有关联"。
无差别邻域扩散下，阻断枢纽能把两跳题从 70% 拉到 100%；有了只沿指定关系走的关系链模板之后，
差距缩小到关系路径 90% → 100%、三跳 93.3% → 100%——**模板本身已经绕开了 APPEARS_IN 这类边**。

阈值也有代价：「羊村」只连着 8 条边，没到阈值 12，于是"喜羊羊和灰太狼是什么关系"会找到一条
4 跳弱关联（同住羊村的暖羊羊 → 暖羊羊的好朋友蕉太狼 → 蕉太狼的二叔灰太狼）。

**⑤ 实体消歧：子串不等于简称，向量不能单独拍板**

公司名里"星海资管"⊂"星海资产管理有限公司"几乎总是简称；角色名里却经常相反：

```
「和平星」⊂「射手座和平星」      总称与个体   —— 首版把三颗和平星并成了一颗
「卡布达」⊂「卡布达巨人」        机器人与它的变身形态 —— 修完一次又被 LLM 抽取撞上
```
最后的规则是四级级联：**文档声明的「又名」**（最强证据，免费）→ 规范化相同 → 前两字相同的进入灰区交
LLM 裁决 → 其余一票否决。另加一条 cannot-link：**同一份文档里有关系边相连的两个名字，必不是同一实体**
（高圆寺寅彦是高圆寺让的爷爷，这两个名字前三个字相同、向量高度相似）。

## 四、架构

```
┌──────────────────────────────────────────────────────────────┐
│ web/index.html  零外部依赖单页（原生 SVG 画关系图，断网可用）    │
│   问答 │ 可点击引用 │ 证据溯源 │ 关系路径 │ 路由与耗时         │
└───────────────────────────┬──────────────────────────────────┘
                            │  FastAPI (src/graphrag/api.py)
┌───────────────────────────▼──────────────────────────────────┐
│ RAGService  —— 评测脚本与 HTTP API 共用同一套装配              │
│  ┌ QueryRouter ───── 规则路由: 属性类 / 关系类 / 聚合类        │
│  ├ RoutedRetriever ─ 级联: 主路先发, 备选补齐剩余预算          │
│  │    ├ lexical: RRF(BM25 + Dense)                           │
│  │    └ graph:   实体链接 → 意图模板(关系路径/关系链/邻域)      │
│  │               → 枢纽阻断 → 文档内挑证据块                    │
│  └ AnswerGenerator ─ 带引用生成 + 引用回验 + 拒答护栏          │
└──────┬──────────────────────────────────┬────────────────────┘
       │                                  │
┌──────▼──────────────┐      ┌────────────▼───────────────┐
│ chunks + 向量        │      │ KnowledgeGraph (内存)       │
│ BM25(中文混合分词)   │      │  BFS / 多路径枚举 / 溯源     │
│ Dense(ONNX, 离线)   │      │  接口对齐 Cypher 表达力      │
└──────▲──────────────┘      └────────────▲───────────────┘
       └──────────┬───────────────────────┘
        ┌─────────┴──────────────────────────────┐
        │ Ingest: 切块 → 抽取(LLM/规则) →          │
        │         schema 校验 → evidence 回查 →    │
        │   实体消歧(又名/规则/向量/LLM + cannot-link)│
        └────────────────────────────────────────┘
```

### 四个刻意的"不做"

| 不做 | 理由 |
|---|---|
| **不用 Neo4j** | 几十个节点、不到两百条边，内存图遍历几十行搞定，零外部依赖。接口对齐 Cypher 表达力，换库只动 `store/graph.py` 一个文件 |
| **不用 LangChain** | 检索逻辑是本项目的核心论点，包进框架就无法做组件消融，面试被追问"这一步发生了什么"也答不上来 |
| **不用 FAISS/HNSW** | 187 个向量，暴力内积毫秒级（含 BM25 在内单次检索约 2ms），比建索引还快。引入 ANN 会带来召回率损失这个新变量，干扰消融结论。切换点约在十万级 |
| **不用 rank_bm25** | BM25 一共 40 行。包进第三方库连"为什么 b=0.75"都答不上来 |

## 五、Prompt 工程：把 prompt 当代码管

Prompt 不内联在 Python 里，而是 `prompts/<用途>/<版本>.md` 的版本化文件：

```markdown
---
id: answer/v3_guarded
base: answer/v2_cited
changes: 加拒答护栏；区分"资料没有"与"资料有但不完整"；多跳题要求先列证据链
hypothesis: 陷阱题拒答率应大幅上升；风险是矫枉过正，本来能答对的题开始拒答
---
# system
...
```

`hypothesis` 是刻意设计的：**改 prompt 之前先写下预期，跑完评测再对照。
预期错了比分数没涨更有价值 —— 那说明你对失败模式的理解是错的。**

| 家族 | 演进 |
|---|---|
| `extract_triples/` | v1 朴素 → v2 封闭 schema → v3 few-shot（含 2 个**负例**：套话段落、凭记忆补全）→ v4 读懂列表结构 |
| `answer/` | v1 朴素 → v2 强制引用 → v3 拒答护栏 |
| `router/` | LLM 分类器，对照组是手写规则 |
| `resolve_entity/` | 只裁决灰区候选对，不做全量两两比较 |

### 抽取 prompt 的演进（DeepSeek，42 份文档）

| 版本 | precision | recall | F1 | 发生了什么 |
|---|---|---|---|---|
| v1 朴素 | — | 0% | 0% | 没给 schema，模型自创了 entities/relations 格式和中文关系名，一条都用不上 |
| v3 few-shot | 98.0% | 86.2% | 91.7% | 居民登记、学生名册、阵营一览**整份跳过**：LIVES_IN / FACTION 召回 0% |
| **v4 结构感知** | 96.7% | **100%** | **98.3%** | 把"不推理"细化为"不许臆测，但必须读懂排版"，补一个列表型正例 |

v3 的问题正是 v4 的 hypothesis 里预先写下的；代价（precision 降 1.3 点）也在预期之内。

### 评测必须同时看答对率和拒答率

```
只看拒答率 → 永远回答"资料中未提及"的系统能拿满分
只看答对率 → 从不拒答的系统在陷阱题上全错，但总分未必难看
```

**单看任何一个都能被轻易刷分 —— 这是 prompt 调优最容易自欺的地方。**

这两部动画模型本来就看过，所以陷阱题特意挑了**现实中有答案、但语料里没有**的问题
（"喜羊羊的妹妹叫什么"），考的是"只依据资料"而不是"知不知道"。

三版 answer prompt 的实测（DeepSeek，全部 109 题，抽取图）：

| 指标 | v1_naive | v2_cited | v3_guarded |
|---|---|---|---|
| 可答题答对率 | **90.7%** | **90.7%** | 88.7% |
| 陷阱题正确拒答 | 100% | 100% | 100% |
| 可答题误拒答率（拒答且没答对） | **6.2%** | 7.2% | 11.3% |
| 引用命中标准证据 | 86.9% | **92.1%** | 91.7% |

> 本表是**关键词判分**口径（与历史结果可比）。关键词判分对关系类题偏宽，用 LLM 判官复判后，v3 的可答题答对率从 88.7% 降到 86.6%，见 [07-Agent](docs/07-Agent.md)。

v3 的 hypothesis 写的是"拒答率大幅上升，风险是矫枉过正"。**收益没发生**——连无约束的 v1
都是 100% 拒答；**风险应验**——误拒答 6.2% → 11.3%，答对率掉了 2.0 点。

这张表第一版长得不一样：v1 陷阱题"只拒答了 91.7%"、v2 "83.3%"，v3 误拒答 20.6%。
翻开原文才发现**都是判分器的问题**：
- "没有关于卡布达体重的信息""现有信息中没有记载"没被拒答关键词认出来——看起来像模型编了答案
- v3 在关系路径题上 5/5 答对（"儿女亲家""表亲"；这是当时的判分口径，q-0088 收紧后为 4/5），只是开头先写了一句"资料中未提及直接关系"，
  被当成了拒答——看起来像护栏矫枉过正

修法：补全拒答措辞；误拒答改为"拒答**且**没答对"。**评测代码本身也要被评测。**

抽取图 vs 标准图：可答题答对率 **88.7% vs 89.7%**，差 1 题（q-0088）。v4 抽取 recall 100%，没有漏边；差距来自抽取图**多记**的一份来源文档：它占掉一个检索名额，把「阵营一览」挤出了 top-8。（这道题收紧判分前两张图都被判对，见 [07-Agent](docs/07-Agent.md)。）

### 三个环节的对照基线

| 环节 | 基线（零 LLM） | 意义 |
|---|---|---|
| 抽取 | `RuleExtractor` 正则 | 回答"LLM 比规则强在哪"。**规则在模板语料上 F1 100%，但不具外推性** |
| 路由 | 手写关键词规则 | 在窄领域里 LLM 未必赢。**没验证过就上 LLM 是信仰不是工程** |
| 生成 | `ExtractiveGenerator` 直出原文 | **分清是检索好还是模型好** |

## 六、LLM 与向量：都是可切换 provider

### LLM 层（`src/graphrag/llm.py`）

| `GRAPHRAG_LLM` | 说明 | 用在什么时候 |
|---|---|---|
| `claude` | 原生 citations + 严格 schema | prompt 调优、最终对比 |
| `deepseek` | 成本约 1/20 | 日常开发、批量抽取（本仓库的缓存由它录制） |
| `ollama` | 本地模型，完全离线免费 | 没有 key |
| `replay` | **只读磁盘缓存，零网络零调用** | **面试演示** |

能力差异不靠 `if provider == "claude"` 散落各处，而是声明在 `CAPABILITIES` 表里，
上层查询后选择实现路径：

| | Claude | DeepSeek / Ollama |
|---|---|---|
| 严格 schema 约束 | 原生 | 只有 JSON mode → 校验+错误回灌重试 |
| 字符级 citations | 原生 | 无 → "标记 + span 回溯对齐" |

**缓存在 provider 之前**，按 `hash(model + prompt + 参数)` 落盘。解决四件事：

1. **演示确定性** —— 现场用 `replay`，不会出现"这次答得不如上次"的当场翻车
2. **评测可复现** —— 分数不随采样漂移，"这版 prompt 涨了 3 分"才是真涨
3. **成本可控** —— 消融实验反复跑十几轮，无缓存就是十几倍开销
4. **降级无硬失败** —— 没设 key 时自动退到 `replay`，别人拿到仓库也能跑通

成本量级（DeepSeek 实测）：四版抽取 prompt 跑完全部语料合计约 $0.14；三版 answer prompt 各答一遍 109 题，每版约 $0.02。

### 向量层

| `GRAPHRAG_EMBED` | 装机体积 | 首次运行需联网 | 备注 |
|---|---|---|---|
| `onnx` | ~50MB | ❌ | `bge-small-zh` 量化版 24MB **随仓库分发**，推荐 |
| `st` | 数百 MB | ✅ | sentence-transformers |
| `none` | 0 | ❌ | 退化为纯 BM25，**零依赖兜底** |

`none` 不是降级方案，**它本来就是消融实验的基线行**。副作用是：
即使目标机器什么都装不上，demo 依然能完整演示，只是评测表里 dense 那几列空着。

## 七、运行

### 环境要求

- **Python ≥ 3.10**（唯一硬性要求）
- Phase 0 全程标准库，**无需 pip install、无需 Docker、无需数据库、无需 API key**

### Windows

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1

python run.py doctor                    # 环境自检（含中文编码验证）
pip install -r requirements.txt         # 可选：启用向量检索与 Web 演示
python run.py fetch-model               # 可选：下载 24MB 向量模型
python run.py all                       # 全流程
python run.py serve                     # http://127.0.0.1:8000
```

> **关于中文乱码**：`src/graphrag/compat.py` 在启动时把 stdout 重设为 UTF-8，
> 并对旧版 `cmd.exe` 调用 `SetConsoleOutputCP(65001)`。所有文件读写一律显式
> `encoding="utf-8"`、`newline="\n"`，保证 Windows 与 macOS 产出**字节一致**。
> 若仍有乱码，优先使用 Windows Terminal / PowerShell 7。

> **搬到另一台机器**：`.venv/` 不能跟着走（绝对路径 + 平台专属 wheel），
> 依赖必须在目标机重装。但 `models/` 目录可以直接拷贝 ——
> 拷过去后目标机**无需联网**即可使用向量检索。

### macOS / Linux

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python run.py all && python run.py serve
```

### 全部任务

| 命令 | 作用 |
|---|---|
| `python run.py doctor` | 环境自检 |

## 九、已知缺口

| 缺口 | 现状 | 方向 |
|---|---|---|
| 语料规模 | 42 份文档，k=10 已覆盖相当一部分语料，检索的绝对分数偏乐观 | 补充分集剧情梗概；但只收可核实的事实，宁缺毋滥 |
| 纯语义题 | recall@10 66.7%（纯 Dense 75.0%） | 换更大向量模型 / 加 cross-encoder rerank |
| 枢纽阈值 | 固定为 12；「羊村」这类小枢纽仍会产生弱关联路径 | 按节点类型或边类型设阈值 |
| 关系链模板 | 关系词表是手写的，只覆盖本题材的称谓 | 与 LLM 查询解析做对比（Phase 3 计划） |
| 列举比较题 | 图检索只有 72.2%：「正义阵营有哪些机器人」里的「正义」是字面量，链接不到任何实体 | 字面量节点也建索引，作为检索起点（不作中转） |
| 拒答判定 | 仍是关键词匹配，补过一轮措辞；新的说法出现时还会漏判 | 让模型输出结构化的 answered / refused 字段，或用小模型做判定并抽检 |
